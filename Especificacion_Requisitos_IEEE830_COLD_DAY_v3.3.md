# 1\. Introducción

## 1.1 Propósito

El presente documento constituye la Especificación de Requisitos de Software (SRS) formal para la plataforma tecnológica COLD DAY, elaborado bajo los lineamientos del estándar IEEE 830-1998. Su propósito es definir de manera exhaustiva, estructurada y verificable los requisitos funcionales y no funcionales del sistema, organizados en dos fases estratégicas: Fase 1 (Núcleo Operativo / MVP) y Fase 2 (Escalado Comercial, Transaccional y Fiscal), incorporando la política de control de recaudo en efectivo, retención de comisiones y desbloqueo operativo mediante consignación bancaria.

## 1.2 Alcance del Producto y Estrategia por Fases

COLD DAY es una solución integral de intermediación y gestión operativa para servicios técnicos especializados en refrigeración, climatización, electricidad y reparación de electrodomésticos. El alcance se estructura en:

- Fase 1 (MVP – Núcleo Operativo / Etapa Productiva): Implementación del portal comercial y la app operativa como frontend unificado en Angular (SEO vía Angular Universal/SSR, APK condicional vía Ionic/Capacitor), autenticación con JWT, verificación documental de técnicos con control de vigencia, geolocalización espacial mediante PostGIS, ciclo de vida de órdenes de trabajo (OT), chat interno por WebSocket, notificaciones push vía FCM, actas de garantía digital (Ley 1480), registro trazable de pagos en efectivo/transferencia, control de recaudo en efectivo con inhabilitación temporal hasta validación de consignación bancaria, gestión de disputas y panel administrativo de auditoría.
- Fase 2 (Escalado Comercial, Transaccional y Fiscal): Incorporación de pasarela de pagos digital automatizada (split payment), liquidación porcentual automática, modelo de suscripciones para técnicos, facturación electrónica certificada ante la DIAN, catálogo/marketplace de repuestos y gestión de contratos recurrentes B2B.

# 2\. Descripción General

## 2.1 Perspectiva del Producto y Arquitectura

El sistema opera bajo los principios de Clean Architecture, desacoplando la lógica de dominio de las interfaces y frameworks tecnológicos. A partir de la revisión de arquitectura del 28 de agosto de 2026, el portal comercial y el aplicativo operativo se unifican en un único frontend Angular, en lugar de mantener dos frontends independientes (decisión anterior de Astro + Flutter), con el fin de reducir el tiempo de desarrollo del equipo reducido del proyecto:

- Capa de Presentación (Angular + Angular Material): SPA responsive única que sirve tanto el portal comercial (SEO, captura de leads) como la operación de campo (tracking en mapa interactivo, timeline de OT, diagnóstico digital, módulo de comprobantes de consignación y chat en tiempo real) para clientes, técnicos y administradores.
- Empaquetado Nativo Condicional (Ionic + Capacitor): si el negocio aún requiere distribución como APK en Google Play, la misma base de código Angular se empaqueta con Ionic/Capacitor para generar el build nativo Android, sin mantener un segundo frontend.
- Capa de Negocio y Servicios (Java / Spring Boot 3.x): API RESTful con control de acceso RBAC (Spring Security + JWT), reglas de validación de disponibilidad y control de deudas de intermediación, documentada bajo OpenAPI 3.x (RNF-11).
- Capa de Persistencia Espacial (PostgreSQL + PostGIS): Base de datos relacional con indexación espacial GiST para geocálculo de distancias y filtros de disponibilidad activa.
- Infraestructura y Servicios Satélites: Despliegue en Docker, canal de notificaciones Push mediante FCM (HTTP v1) y WebSockets (WSS) para mensajería bidireccional.

## 2.3 Restricciones de diseño e implementación

El desarrollo del sistema COLD DAY está sujeto a las siguientes restricciones, derivadas del contexto académico-empresarial del proyecto y de las decisiones tecnológicas adoptadas:

### Restricciones tecnológicas (Fase 1)

- Backend en Java con Spring Boot 3.x, persistencia en PostgreSQL 15+ con PostGIS 3+, autenticación JWT sobre Spring Security, frontend unificado en Angular (Angular Material) para portal y operación, despliegue en contenedores Docker y notificaciones vía FCM HTTP v1.

### Restricciones de plataforma

- La aplicación Angular es responsive y cubre navegadores de escritorio y móvil . Si el negocio requiere distribución en tienda como APK, la misma base de código se empaqueta con Ionic/Capacitor para Android 8.0 en adelante.

### Restricciones de recursos

- Equipo técnico reducido y priorización de servicios de bajo costo (ej. OpenStreetMap).

### Restricciones normativas

- Cumplimiento de Leyes 1581, 1273 y 1480 en Fase 1; Resolución DIAN 000042 y Ley 1266 en Fase 2.

### Restricciones de idioma

- Interfaz y documentación exclusivamente en español (Colombia).

## 2.4 Suposiciones y dependencias

- Suposiciones: Conectividad a internet intermitente en campo, técnicos con Android 8.0+ y GPS habilitado, y veracidad de datos declarados por usuarios.
- Dependencias externas: Firebase Cloud Messaging, proveedores de mapas (OpenStreetMap/Google/Mapbox — decisión de proveedor definitivo aún pendiente de cierre, ver observación en el informe de revisión), aprobación de cuenta en pasarela de pagos y habilitación ante la DIAN para Fase 2.
- Dependencias organizacionales: Financiación e hitos de seguimiento del Fondo Emprender.

# 4\. Interfaces del Sistema

## 4.1 Interfaces de Usuario (UI)

- Aplicación Web/App Operativa Unificada (Angular): landing comercial orientada a conversión (con SSR para SEO), catálogo de servicios, formularios de captación corporativa, mapa interactivo con radar espacial, timeline de estados, formulario estructurado de diagnóstico, pantalla de carga de comprobantes de consignación bancaria y chat en vivo — todo dentro de una sola base de código responsive.
- Empaquetado Nativo Condicional (Ionic + Capacitor): si el negocio requiere distribución adicional como APK en Google Play, se genera a partir del mismo proyecto Angular, sin duplicar frontend.
- Panel de Administración Web: Interfaz de validación de documentos técnicos, módulo de conciliación de consignaciones en efectivo con botones de aprobación/rechazo, bandeja de gestión de disputas (RF-F1-25) y monitoreo de OT en tiempo real.

## 4.2 Interfaces de Software y Conectores

- Motor Geoespacial: PostgreSQL 15+ con extensión PostGIS 3.x.
- Servicio Push: Firebase Cloud Messaging (FCM HTTP v1).
- Pasarela de Pagos (Fase 2): Conectores Webhook REST con pasarelas autorizadas (Wompi / PayU).
- Facturación DIAN (Fase 2): Consumo de API REST/SOAP del proveedor tecnológico habilitado.
- API interna documentada bajo OpenAPI 3.x / Swagger (RNF-11). **\[NUEVO\]**

## 4.3 Interfaces de Comunicación

Protocolos estándar HTTPS con REST API para operaciones transaccionales y WebSockets seguros (WSS) para mensajería en vivo y monitoreo de estado.

# 6\. Conclusión y Viabilidad del Proyecto

La versión 3.3 del SRS IEEE 830 consolida el control financiero y operativo del modelo inicial de recaudo contra entrega en efectivo, e incorpora las correcciones identificadas en la revisión del 26 de agosto de 2026: separación formal del requisito de gestión de disputas (RF-F1-25), un requisito explícito de registro de pago en efectivo/transferencia (RF-F1-26), control de vigencia de certificaciones del técnico, desactivación de geolocalización post-servicio (RF-F1-27), ampliación de los requisitos no funcionales (RNF-07 a RNF-11), el cierre definitivo del modelo de despacho: difusión (broadcast) simultánea a técnicos dentro de un radio de 10 km, con ventana de aceptación de 60 segundos y expansión de +5 km hasta un máximo de 25 km si nadie acepta (RF-F1-07 / RF-F1-09 / RNF-03), dado que todos los servicios se tratan como urgentes en Fase 1 (RF-F1-08); y la migración de arquitectura del 28 de agosto de 2026: frontend unificado en Angular para portal y app operativa, con empaquetado nativo condicional vía Ionic/Capacitor (RF-F1-16 a RF-F1-18, sección 2.1).

Queda pendiente de decisión por el equipo el cierre de la selección de proveedor de mapas y de pasarela de pago, puntos que se documentan en el Anexo A. Esta especificación garantiza la sostenibilidad del negocio al bloquear la asignación de nuevos servicios a técnicos con deudas de comisión pendientes, manteniendo la arquitectura abierta para la transición automática a pasarela digital en la Fase 2.
